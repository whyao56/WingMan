## 0.1.0 —— 从「能跑」到「能装」「能自查」

**起点。** 代码在本机能跑通，但一个陌生人拿到仓库装不起来：不知道要哪个 Python、
依赖装不上、端口被占了只会看到一句英文报错。这一版要把这条落差补上。

**做法。** 根目录放一个 `wingman.cmd` 作为唯一入口：首次运行自动建环境、装依赖、
起服务、开控制台。启动前的自检按四类问题（Python 版本过低 / 端口占用 / 数据目录不可写 /
依赖安装失败）分别给出中文修复建议，并且**失败时不留下半成品环境** —— 这一条比报错文案
更重要，否则用户第二次运行会踩到一个状态更乱的仓库。

运行期另有一条自检通道：`--doctor` 体检仓库完整性与依赖，`/api/health` 保持最小只读契约
（`scripts/e2e_check.py` 依赖它），新增的 `/api/health/details` 则逐键标注配置来源
（`runtime` / `env` / `dotenv` / `default`）。**密钥在所有这些输出里一律以掩码出现** ——
自检报告会被贴到 issue 里，它不能成为泄漏渠道。

**然后是打包。** PyInstaller 出绿色免安装目录，`scripts/make_release.py` 把
「打包 → 算校验和 → 建 Release → 传附件」串成一条命令，并且刻意把时间戳钉死、
文件顺序排序，让**打包这一步可复现**。

**踩到的坑（都在打包环节）。**

- **本地转写输出乱码但不报错**：调用方传进来的是「int16 量级的 float32」（值域 ±32768，
  只是 dtype 被转成了 float32），而代码只按 dtype 判断要不要归一化，于是把放大三万倍的
  波形喂给模型。修法是加峰值兜底，三种量纲形式的输出改为逐字一致。
- **自检把「模型没下载」报成绿色「已完成」**：原先用 `available`（对象构造得出来）判断，
  而本地 whisper 在权重一个字节都没下载时它也是 `True`。拆出 `ready`（现在能不能真的出字）
  与 `not_ready_reason`（差在哪）。
- **`hf_xet` 是纯死重量**：它是 `huggingface_hub` 的可选加速后端，被自动探测到就会进包，
  而项目无条件禁用了 Xet，于是它白占约 9 MB。

**验证。** CI 在 Ubuntu 上用 `requirements.lock.txt` 真实安装并跑冒烟测试，
Python 3.11 与 3.13 两个 job 均通过。

## 0.1.1 —— 把「填了也连不上」修掉

**起点。** 0.1.0 发出去之后收到的反馈集中在两件事：一是设置页填了云模型的地址和 Key
点「测试连通」连不上；二是界面「太 AI 味」，排版也挤在一起。

**根因。** 第一条不是网络问题 —— 是**预设里的模型名已经过期**，用户照着预设填，
服务端自然拒。这类「我们的默认值比现实旧」的故障最难自查，因为它表现成用户的配置错误。

第二条是一个典型的前端静默坑：**两个同名 CSS 类在互相覆盖**，谁生效取决于样式表里的
先后顺序。改的时候没有任何报错，只是看起来「挤」。

**做法。** 整体视觉重做，并把新手路径上的文案与默认值一起过了一遍 —— 默认值也是接口的
一部分，它过期了和接口坏掉是同一种后果。

**顺带更正了一处旧说法。** 0.1.0 的说明里写过「同样的代码重打一次会得到字节相同的 zip」，
这**只对「打包」这一步成立**：`dist/` 是 PyInstaller 生成的，那个构建不是逐字节确定的
（同一份源码连构建两次，219 个文件里有 2 个不同）。校验和的正确用途是核对**下载**是否
完整，不是核对构建是否可复现。这条更正保留在各版说明里。

## 0.1.2 —— 不用再导出文件：采集层

**起点。** 导入聊天记录必须先自己导出成文件，这一步把大量用户挡在门外。

**做法。** 新增一整层 `backend/app/collect/`：`detect`（探测进程 / 版本 / 数据目录）、
`matrix`（版本支持矩阵）、`keys`（取密钥）、`sqlcipher`（解密）、`reader`（认列 + 读消息）、
`pipeline`（六道关编排），以及半自动通道 `clipboard` + `semi`。两条通道**并列**，
不是一条主路加一条备胎 —— 自动采集受制于客户端版本和加密方式，半自动（选中消息复制、
程序读剪贴板）不依赖能否读取加密库。

两个刻意的设计决定：

1. **版本支持矩阵写进软件，不写进 README。** 文档不会知道用户装的是哪个版本，
   而 `collect/matrix.py` 里是实测过的版本数据，界面把探测结果和矩阵合起来给结论，
   四档结论每一档都带照做的事。
2. **时间推定必须可查、可筛、可标注。** 数据模型只比导入多两个标记：`chats.source`
   （`import` / `collect`）与 `messages.ts_source`（`exact` / `assumed` / `manual`）。
   剪贴板经常不带时间，若用「抓取时刻」顶替，真时间轴上就混进了假时间 ——
   「她平时几点找我说话」这类结论会直接错掉。

**踩到的坑。**

- **采集层在非 Windows 上「导入即失败」**：`winapi.py` 与 `clipboard.py` 顶上各有一行
  模块级的 `from ctypes import wintypes`，而 `ctypes.wintypes` 里的 `VARIANT_BOOL` 用了
  `'v'` 类型码，那个码只有 Windows 版的 `_ctypes` 认识，Linux 上直接抛
  `ValueError: _type_ 'v' not supported`。它与有没有调用无关，是**模块级语句**，
  所以表现是「本地 Windows 全绿、一推上去整个 CI 矩阵全红」，而报错跟采集看起来毫无关系。
  现在由 `winapi.py` 统一决定 `wintypes` 是什么（Windows 上导不进来会直接 re-raise，
  **不许用替身把真故障盖过去**），并加了反向用例防止守卫自己变成空测。
- **同一个接口注册在两处**：`/api/collect/cursors` 一度同时出现在两个路由文件里，
  运行时先注册的那个生效、后一个完全收不到请求 —— 改哪一份都不一定有用，而读代码看不出来。
- **响应注解写错导致接口 500**：`/api/collect/matrix` 返回列表但注解写成 `dict`，
  FastAPI 按注解校验返回值，接口实际是 500，在界面上表现成「点了没反应」。
- **重置游标静默删 0 条**：`account` 对不上时静默删 0 条却照样返回成功，
  用户点「重置」以为好了，下次采集还是从老位置继续。

**验证。** 真库密钥拿不到的情况下，按 SQLCipher 规格**自己造库再解回来**，
这是唯一能证明解密器写对的验证方式；剪贴板解析覆盖 QQ 多选复制主形态、
认不出说话人时必须拒绝、正文里的日期不许被当成消息时间。

## 0.1.3 —— 只修一件事

**起点。** 0.1.2 有个明显缺陷：点采集报一句英文 `Failed to fetch`。

**根因不在采集逻辑里，而在 HTTP 连接的生命周期。** uvicorn 的 `timeout_keep_alive`
默认 5 秒，空闲超过 5 秒就把连接关掉；浏览器并不知道，仍在这条已经死掉的连接上发下一个
请求，拿到零字节响应。**GET 会被浏览器静默重试、POST 不会** —— 所以只有采集（全是 POST）
报错，而那句英文是浏览器原话，不是本程序的文案。

**做法。** 服务端把 `timeout_keep_alive` 显式设为 `KEEP_ALIVE_S`（600 秒），
两个启动入口走同一个常量；前端在**网络层失败**时重发一次（这类失败意味着请求根本没到
服务端），并把英文原话换成能照做的一句中文；采集按钮上显示已等待秒数。

**顺带修的三个「承诺了时间却做不到」的地方。**

- 「自动找密钥」的时间预算**只在外层循环查了一次**：第 1 级（逐进程读内存 + 正则扫十六进制）
  一次都没查，第 2 级的内层循环也查不到。实测本机（7 个 QQ 进程、2.9 GB 可读内存）
  第 1 级合计 43 秒、单个 8.4 MB 锚点区域穷举 157 秒，而界面承诺的是「预演 12 秒 / 采集 60 秒」。
  现在预算贴在每一层循环上，并把「到点收工」和「扫完了没找到」分成两句不同的话 ——
  前者不能下结论。
- **不再对全文索引库白跑一遍取密钥**：`*_fts.db` 里只有分词索引、没有消息行，
  本机 QQ 会被挑出 7 个「消息库」其中 4 个是索引库，用户等的时间是原来的 7 倍。
- 同一个客户端只搜一遍内存密钥（内存内容几秒内不会变），验证通过的密钥先拿去试。

**验证。** `test_http_keepalive.py` 真的起服务、真的「GET → 空闲 6 秒 → 同一条连接上 POST」，
旧配置下会失败。

## 0.1.4 —— 以「对象」为中心

**起点。** 之前的软件是「先有会话、再看会话」，一个人在多处（微信 + QQ + 换了昵称的老号）
说过的话是散的，得用户自己对着拼。

**做法。** 把「对象」提为第一层、渠道降为第二层；新增指挥台（先选对象、再勾渠道，
可多选）；输出会留存；聊天记录可二次编辑；导入支持拖放与多文件；桌面版右上角 × 会先问
一句「关闭程序 / 后台运行」；侧栏常驻自检提醒。

**踩到的坑。**

- 半自动采集「第一次正常、第二次报错」。
- 前端调用了不存在的函数 —— 这一处是本轮改版自己引入的，属于「改 A 忘了 B」。

两条都指向同一个教训：**新加的界面元素要连同它调用的接口一起验**，
只在人工点一遍主路径是不够的。

## 0.1.5 —— 先填后补，以及「别的聊天也算数」

**起点。** 0.1.4 把记忆的中心换成了「对象」，但顺序是**固定**的：必须先把聊天记录导进来，
程序才会替你建出那个对象。另一件事是渠道只有 QQ 和微信两个位置，
Telegram / 钉钉 / 短信 / 贴吧里说的话无处安放，只能硬塞进微信。

**做法。**

- **对象可以提前新建，只填名字就能建**，关系、期望关系、阶段目标、备注之后再补。
- **「让 AI 帮我整理」在你的草稿上补，而不是重写一份**：把这个人名下全部渠道的消息
  加上已记住的事实合起来交给模型，逐项回报「保留了你手写的 XX」/「已更新 XX」。
  默认只填空、不动手写内容；想连手写的一起改写要再点一次确认。
- **新增「其他聊天」渠道**：它是一个**明确定义的位置**，不是「认不出来的东西」。
  剪贴板采集可以直接选它 —— 内容是你自己复制的，不依赖能否读取加密库。
- **预先新建的空对象会接住之后的同名导入**：判据是「那个名字下一段记录都没有」，
  空对象里没有任何数据，接住它不可能混掉谁的记忆。

**挖出来的三个「静默坏了很久」的问题。**

1. **导入微信聊天记录必然崩溃**：适配器从项目第一个提交起就引用了一个从未导入的名字
   （`NameError: iter_blocks`），所以这条路**一直没通过**，连仓库自带的示例文件都读不出来。
   它能坏这么久，是因为当时没有任何测试跑过微信适配器。现在两份示例文件都被端到端钉住，
   另加一条静态守卫：`app/` 下任何模块都不许引用「既没定义也没导入」的全局名 ——
   这一类错编译不报、导入不报，只在真跑到那一行时才炸。
2. **「检查更新」显示成旧版本号**：根因不是文案写错，而是**一个旧进程还在 8787 端口答话**。
   页面是每次从磁盘现读的（新的），服务却是一个长驻进程（旧的），于是「界面是新的、
   版本号是旧的」。除了清进程，还加了三层防呆：前端自带 `BUILD` 常量并与 `/api/health`
   比对，不一致就在页面顶部弹红横幅；`/api/desktop/state` 自述
   `version / started_at / uptime_seconds / mode / pid`；HTML 响应加 `Cache-Control: no-store`。
3. **通用 JSON / CSV 导入的列名匹配是失效的**：`_resolve_map` 把「候选列名表」当成了
   「数据里实际有的列名」，于是永远只返回候选表的第一个名字。最坏的地方是
   **嗅探和解析说两套话**：`sniff` 看到中文表头给 0.85 高分、用户看到「匹配度很高」，
   然后一条都没导进去。

**另一处修正**：半自动采集只填了称呼、库里已有同名的人时，会按「对方称呼」再新建一个人
—— 采一次多一个「小鹿」，而这两个小鹿的消息永远检索不到一起。改为先按名字/别名
**精确**复用（不做模糊匹配，合并永远由用户显式发起）。

## 0.2.0 —— 关窗死锁与内存瘦身

**起点。** 用户报了两件事：**点窗口右上角 × 总会卡住，Windows 显示「WingMan 未响应」**；
以及内存占用偏大。「总会」这个词是关键线索 —— 它说明是确定性故障，不是偶发。

**第一步：先复现，不猜。** 对窗口发 `WM_CLOSE`，然后用 `Process.Responding` 读状态，
**连续 8 秒都是 `False`**，同时 CPU 时间死死钉在 2.0625s 不动。真在计算的话 CPU 会涨；
纹丝不动说明它纯粹在等 —— 这是**死锁**，不是「算不过来」。

**根因：UI 线程里的同步 `evaluate_js`。** `_on_closing` 这个钩子跑在 UI 线程上
（winforms 的 `FormClosing` 回调），里面却同步调用了 `evaluate_js`。而 pywebview 的实现是：
把脚本投递到 UI 线程执行，然后等一个 `semaphore.acquire()`——**没有超时**；
负责释放它的回调也被投递到 **UI 线程的同步上下文**，而 UI 线程正卡在钩子里等它。
互等，必死。

**修法与三层兜底。** 钩子只置标志 + 起后台线程，**绝不在 UI 线程上碰任何同步 JS 调用**；
通知界面套 5 秒超时；界面接不住就直接补关窗；再加 `quitting` 标志放行后续的关闭事件。
第三层是为了不让「修卡死」变成「点了没反应」。

**内存：一个 `import` 占了九成。** 先用「空 Python / 只导入依赖 / 完整服务」三组对照
分层测量，结论很清楚：**自身代码只占 11 MB，780 MB 全是导入 numpy 时 OpenBLAS
按 24 个逻辑核开的线程池**。A/B 对照：默认 760.6 MB / 27 线程，限流后 19.4 MB / 4 线程。
限流必须写在 `app/__init__.py` —— 它是包最外层，是唯一能保证早于 numpy 被导入的位置，
放进 `config.py` 或 `main.py` 都已经晚了。结果：提交内存 **844.9 MB → 107.0 MB**。

**顺路撞见并修掉的两个真问题。**

- **`_STOP.set()` 是死代码**：全仓搜索无消费者，注释说「先让 uvicorn 收工」是假的，
  实际退出靠 1.2 秒后 `os._exit(0)` 硬切。改成保存 `uvicorn.Server` 引用、置 `should_exit`
  并轮询等它收工。
- **`python -m app.desktop` 下状态有两份**：模块以 `__main__` 执行一次、又被按模块名导入
  一次，导致窗口开着却报 `native_window: false`。

**一个把排查带偏的坑**：内存探针第一次所有读数都是 `0.0 MB`，**不报错只是全 0**。
根因是 `psapi.GetProcessMemoryInfo` 的句柄参数：`GetCurrentProcess` 返回伪句柄 -1，
不声明 `restype` 会被截断成 32 位 int，调用**静默返回 0**。

**验证。** 240 passed / 1 skipped；6 条关键守卫做了脚本化反证（逐条改回旧写法 →
对应用例必须失败 → 自动还原），其中一条反证第一次没抓住，原因是复现旧代码复现得不够忠实
（只改了一处、留着另一处的线程包装），重构后重跑才过 —— 这本身就是反证的价值。
端到端在**源码模式与打包版各跑一遍**：WM_CLOSE 后 Responding 全程 True、
拦截 → 后台运行 → 调回、关闭程序 1 秒内干净退出。

## 贯穿始终的几条做法

回看整个 0.1.x 到 0.2.0，有几条原则反复出现，构成了这个项目的工程习惯：

1. **先复现，不猜。** 0.2.0 用 `Process.Responding` + CPU 读数区分「死锁」与「算不过来」；
   0.1.5 的微信导入是端到端跑一遍才暴露出「从第一个提交起就是坏的」。
2. **静默失败是最危险的一类。** 校验和报 0、`iter_blocks` 未导入、列名匹配永远返回第一个、
   重置游标删 0 条 —— 它们都不报错，只是给出错误结果。修法不只是改代码，还要补一条能
   钉住它的守卫。
3. **守卫要能被反证。** 加完测试不算完，得把它对应的修复改回去、看它是否真的变红；
   反证过程本身也会暴露「复现得不忠实」。
4. **文档要写清「为什么」。** 每一条取舍都记下当时否掉了什么 ——
   因为这些才是在下一次遇到同类问题时真正有用的部分。
