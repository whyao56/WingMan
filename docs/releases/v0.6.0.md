这一版修的是**「点右上角的 × 就卡死」**，顺手把内存里最大的一笔浪费找了出来 ——
那笔浪费占了整个程序内存的九成以上，而它来自一个**只有一行 `import`** 的地方。

---

## 为什么要改

### 1. 点 × 会把窗口卡死

点一下窗口右上角的 ×，标题栏变成「WingMan 未响应」，然后点什么都没反应 ——
任务管理器里那个进程还在，但 CPU 一动不动。

这不是「有点慢」，是**死锁**。

### 2. 内存看起来很大

任务管理器里 WingMan 一直占着好几百 MB。程序本身做的事并不多，
这个数字和它该有的样子对不上。

---

## 这一版做了什么

### 1. 关窗不再卡死

**根因不在界面，在关窗那一刻的线程模型。**

程序的窗口是 pywebview 开的。你点 × 时，Windows 会在 **UI 线程**上回调我们的
关窗钩子；而钩子里要做的事是「叫页面弹一个小窗问你要关程序还是后台运行」，
这需要**在页面里执行一段 JavaScript**。

问题就出在这里：pywebview 的「执行 JavaScript」是一个**同步等待**的操作 ——
它会一直等，直到一个**只能由 UI 线程执行**的回调把结果交回来。
而 UI 线程此刻正卡在关窗钩子里等它。**两边互等，谁都不会先动。**

实测的证据（对同一个进程发 `WM_CLOSE` 并每秒采样）：

| | 修复前 | 修复后 |
|---|---|---|
| 窗口是否响应 | **否**（连续 8 秒） | **是**（连续 8 秒） |
| CPU 读数 | 2.0625s → 2.0625s（纹丝不动） | 正常 |

那个「纹丝不动」正是死锁的指纹：如果是真的算不过来，CPU 会往上走；
这里是**完全在等**。

修法是让钩子**只置一个标志就返回**，把「通知界面」这件事交给一个后台线程去做。
另外加了一个 5 秒超时：万一界面真的接不住，就直接把窗口关掉 ——
**绝不让 × 变成「点了没反应」**。

### 2. 「关闭程序」之前并没有让服务好好收工

顺路查出来的一件事，你可能没察觉，但它有实际风险。

选「关闭程序」时，原代码只 `set()` 了一个事件对象，注释写着「先让 uvicorn 收工，
再结束进程」。但那个事件**从头到尾没有任何地方在读它** —— 也就是说，
uvicorn 从来没收到过退出的信号。

真实的退出过程是：等 1.2 秒，然后**强制结束进程**。

后果是：如果那一刻正好在写数据库（导入刚结束、画像刚存下来），
写了一半就被掐断了。SQLite 的 WAL 模式不会因此损坏数据，但会留下没来得及合并的文件。

现在是真的把退出信号交给 uvicorn，并等它收工（最多 4 秒）再关窗口。
日志里能看到完整的一段：

```
已通知服务收工（uvicorn should_exit）。
WingMan 已退出
Application shutdown complete.
Finished server process [12460]
服务已收工。
```

### 3. 内存：一个 `import` 就占了九成

这是这次最有意思的一处。

程序用 numpy 做一件事：算几千条聊天消息向量之间的**余弦相似度**。
这个规模的运算，连一次眨眼都用不了。

但 numpy 背后的 OpenBLAS 会看你的 CPU **有多少个逻辑核**，然后开同样数量的线程，
并给每个线程预先留出工作缓冲区。这台机器有 24 个逻辑核 —— 于是它开了 24 个线程。

实测（同一台机器、同一个环境，只是 `import numpy` 这一下）：

| | 提交内存 | 线程 |
|---|---|---|
| 默认 | **760.6 MB** | 27 |
| 限制成单线程 | **19.4 MB** | 4 |

**760 MB 对 19 MB —— 差 39 倍，就为了那点用不上的并行度。**

限掉之后，整个程序（带窗口）的提交内存从约 **845 MB 降到约 105 MB**，
线程数从 43 降到 20。

具体做法是在程序包里最早执行的地方设了 `OPENBLAS_NUM_THREADS=1`（以及
`OMP_NUM_THREADS` 等几个同族变量）。有两点值得说明：

- **必须在 numpy 被导入之前设**。OpenBLAS 是在 `import` 那一刻就把线程池建好的，
  之后再设环境变量**等于没设**。所以这段代码只能放在包的最外层。
- 用的是 `setdefault` —— **你自己设过就听你的**，我们只是提供一个更省内存的默认值。

### 4. 一个会让排查跑偏的隐藏问题

`python -m app.desktop` 这种启动方式下，窗口状态在内存里存了**两份**。

原因是这个文件会被加载两次：一次作为程序入口（名字是 `__main__`），
一次被 API 层按正常模块导入（名字是 `app.desktop`）。两边的「窗口对象」
「关闭状态」各自独立 —— 主流程写的是第一份，接口读的是第二份。

症状全都是「像功能坏了」，而不是「像状态串了」：

- 窗口明明开着，`/api/desktop/state` 却说你没有原生窗口，界面于是按「浏览器模式」措辞；
- 点「后台运行」时后端读到一个空的窗口对象，回你「已关闭」，**然后什么都没发生**。

现在启动时会把自己登记到 `app.desktop` 名下，任何入口都只有一份状态。

> 说明：`WingMan.exe` 和 `python run_wingman.py` 走的是另一条导入路径，
> **本来就没有这个问题**。但排查问题时很容易被它带偏，所以一并修了。

## 怎么用（3 步）

1. 把 zip **解压到任意位置**（桌面、D 盘都行，路径有中文也没关系）
2. 双击 `WingMan.exe`
3. 界面打开后 →「设置」页最下面就是体检，那里会逐条列出还没配好的项

> ⚠️ **不要只把 `WingMan.exe` 单独拖出来运行。** 旁边的 `_internal` 文件夹是程序本体的
> 一部分，少一个文件都起不来。要挪位置就整个文件夹一起挪。

**想立刻试一下、手上还没有聊天记录？** 不用去找导出文件：
「采集」页最下面有「粘贴文本」，按上面写的格式粘两句话进去就能跑通整条链路。

## 从 0.5.0 升上来

程序和数据是分开存的，**直接下新包解压覆盖旧文件夹即可**，聊天记录和设置都不会丢
（它们在 `%LOCALAPPDATA%\WingMan`）。

这一版**没有数据库结构变化**，没有迁移步骤。

> **如果你之前遇到的是「点 × 卡住」**：升级之后如果还卡，先确认任务管理器里
> 没有残留的旧 `WingMan.exe` —— 卡住的窗口是关不掉的，只能先结束进程再开新的。
> 界面顶部如果出现红色横幅，它会直接告诉你连上的是哪个版本的进程。

## 完整性校验

```text
3b5d97a5c4268c2afa35e6795d511febb59a2f5866992c164889289e29a9910f  WingMan-0.6.0-win64.zip
```

Windows 上校验：

```powershell
Get-FileHash .\WingMan-0.6.0-win64.zip -Algorithm SHA256
```

这个校验和**能**证明你下到的文件完整、中途没被换过；**不能**靠「自己重新构建一次」来复现
—— 生成 `dist/` 的 PyInstaller 构建不是逐字节确定的（同一份源码连构建两次，文件级校验和有差异），
所以你自己构建出来的 zip 校验和一定和上面不一样，那是正常的。
详细说明见 [v0.3.0 的发行说明](v0.3.0.md) 里「这个校验和能证明什么、不能证明什么」一节。

## 这一版**没有**改的

- **「自动采集取密钥」在本机依然没跑通**：本机实测（QQ NT 9.9.20.37051 /
  微信 4.1.13.12）按 SQLCipher 规格穷举 8378 万候选未命中。
  **半自动那条路仍是当下确定能跑通的通道。**
- 建议内容的质量仍受限于模型：默认的 Mock 引擎让整条链路能跑，但建议是空的。
  要真实建议请在「设置」里配上自己的模型 API Key。
- 内存这一版只动了最大的一笔。窗口本身的渲染开销（WebView2）没有再压 ——
  它属于「换个界面方案才能省」的量级，不是这一版的目标。
